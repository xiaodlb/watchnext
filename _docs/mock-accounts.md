## Bounded design choices

These are engineering defaults under delegated authority, not new user answers.

- Keep account views inside the explicit `/mock` workspace and its mounted service instance: entry, register, sign-in, recovery, private-code reveal and account summary. Internal navigation must not accidentally recreate the service or navigate to production account endpoints. A full reload deliberately starts a fresh synthetic instance; no browser storage is added.
- Extend the centralized typed service with register/sign-in/sign-out/recover/account-context operations. Views call that boundary, not local success stubs. Anonymous context and a newly registered account with no memberships are valid results. A clearly labeled seeded account can expose read-only synthetic membership summaries; group selection, invitation resolution and mutations belong to [#56](https://github.com/xiaodlb/watchnext/issues/56). Do not add working-looking group buttons until their owner implements them.
- Username validation mirrors the baseline: trim, 3–32 ASCII letters/numbers/underscore/dot/hyphen, case-insensitive uniqueness with display case retained. Passwords use 12–128 Unicode code points, preserve spaces/case exactly and require exact confirmation for registration/recovery. All entered credentials must be synthetic. Matching values live only in this temporary adapter; no native crypto, real security guarantee or durable session is implied.
- Registration establishes the synthetic signed-in identity and returns its recovery code only in that successful response. Save-and-continue clears the reveal and opens the account summary. Recovery requires username, current synthetic code and confirmed new password, consumes the old proof, returns one replacement reveal and leaves that account signed out. Continuing opens sign-in; the new password works and old password/code do not. Unknown username and wrong password share a safe sign-in error; unknown/wrong/consumed recovery proof shares a safe recovery error. Missing code explains that no retrieval/email bypass exists.
- Codes may be clearly synthetic generated fixture values, unique through rotations within that instance. Context/list operations never return raw codes/passwords. Copy uses the clipboard only after an explicit click, with selectable manual fallback; the app cannot erase an external clipboard. Codes are removed from the rendered view on Continue, navigation, reset and page departure/bfcache restoration. A lost or discarded reveal cannot be retrieved. Clear password/confirmation/proof inputs after a completed submission or departure, never put them in URLs/logs/screenshots.
- Successful identity changes/reset advance context revision; stale callers cannot act as the previous account or restore previous private views. A pending operation captures instance/revision and an abort signal; canceled or stale operations do not commit. Duplicate submits commit once. Recovery invalidates the target account's simulated active session before success; this is only this adapter's state, not real cross-tab/server session revocation. Reload/new tabs remain independent under the foundation lifetime contract.

## Implemented interaction and evidence

Open `/mock` using the isolated launch in [mock frontend](mock-frontend.md). The account section shares the foundation's mounted service and scenario selector. Register, Sign in, Recover account and Account entry are internal buttons, not production routes. **Read account context** demonstrates anonymous or current identity; **Sign out** is safe even when absent. A newly registered account has no groups. The documented sample `Demo.Viewer` / `synthetic password` shows two explicitly read-only synthetic memberships. No group action is implemented here.

Registration and recovery return a selectable private code only on success. Explicit Copy attempts the clipboard, with manual-select fallback; Continue, other account navigation, reset, pagehide and persisted pageshow clear the disclosure. Completed, canceled or departed forms clear secret inputs. A clipboard is external to this app and cannot be erased by the demo. The service's context contains only display identity and read-only memberships, never a password/proof. Simulated codes and passwords exist only in the per-instance Map; this intentionally provides no real authentication, hashing, cross-tab session security or durable persistence.

Use Ready for normal operations, Slow for disabled duplicate submission and Cancel account request, and Unavailable for a safe retryable error. Changing scenario aborts a pending account request. Identity-changing operations advance revision; an old delayed request or duplicate captured context cannot commit. Reset restores the seeded-only anonymous state, clears private views and invalidates pending work. Reload/new tabs create independent instances. Browser departure clears the reveal even when a live document is restored from bfcache; no discarded code retrieval endpoint exists.

Implementation: `frontend/service/contracts.ts` defines concrete account operations/results; `frontend/mock/service.ts` owns validation, identities and proof rotation; `app/mock/accounts.tsx` renders actual forms/readback through that service. Existing production account services, routes, database, schema and dependencies are unchanged. Only the observed Lovable sign-in's centered spacing informs this increment; recovery/registration/reveal are baseline-derived.
